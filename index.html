§1 · abstract

Title & Abstract

The Listing Gap: CTR/Engagement Opportunity Scoring on Ranked Content.

Can a page's pre-existing attributes — position, content type, search intent, length, competition — predict its click-through rate well enough to flag likely under-performers without first checking each page's actual CTR by hand? This study builds a rule-based baseline and a gradient-boosting model on FlyRank's public starter release, validated on a client-level holdout so no client's pages appear in both training and test data. The model did not beat the baseline on raw prediction error — both, in fact, performed worse than simply guessing the average CTR, an honest finding about how hard this problem is at this data scale. But on the metric that actually matters for a ranked action queue — precision@50, catching the true worst performers first — the model clearly won, 0.40 versus a tied baseline sitting at the 0.26 base rate. The result is a working, if modest, first pass at a CTR opportunity queue, with its real limitations named rather than hidden.

§2 · introduction

Introduction

A page can rank well and still underperform. Two pages sitting at the same spot on page one of Google can have very different click-through rates — one capturing its fair share of the traffic its ranking earns, another quietly leaking clicks to a more compelling result next to it. The second page's problem usually isn't ranking. It's the listing: the title, the meta description, whatever makes a searcher choose one blue link over another.

The decision this work supports is narrow and practical: which already-well-ranked pages should a content editor open first to rewrite the listing, rather than spend more effort chasing rank. Every well-ranked page is not worth the same attention — some are already capturing their expected clicks, some are not. This paper builds, tests, and is honest about a first attempt at telling those two groups apart.

§3 · data

Data

This analysis runs on FlyRank's public starter release — a 30,000-row, 32-client anonymized snapshot of 90-day trailing content performance (content_refresh_anonymized.csv) — not the full internship warehouse. I confirmed read access to the warehouse's real schema and file structure (its fact_content_daily_performance table, monthly partitions, and dim_content attributes match the starter release's column names closely), but did not have a query engine available to execute the joins and aggregations the full ~79-million-row fact table would need from this project's working environment. That's a named limitation (Section 6), not a hidden one.

§4 · methodology

Methodology

Label: click-through rate (clicks_90d / impressions_90d) — continuous, observed, never a model input.

Features: average position, content type, search intent, word count, character count, search volume, competition, competition level, and freshness tier — all knowable without ever looking at the page's own CTR.

Baseline (frozen from an earlier pass of this work): predict CTR as the training-set median CTR for the page's position tier — a single number per tier, computed only from training clients and applied to test clients, so no test-client outcome leaks into the number scoring it.

Model: a gradient-boosting regressor on the fuller feature set above, one-hot encoded, same train/test split, same label.

Validation design: a client-level holdout — clients are split into train and test groups, and no client's pages appear in both. Splitting by row instead would let the model learn client-specific quirks and look artificially better than it would on a genuinely new client.

Leakage check — the true CTR and its numerator (clicks) are excluded from the feature list, confirmed by an assertion in code, not just asserted in prose. Client overlap between train and test was checked and confirmed at zero.

Results — model vs. baseline, same split

Baseline — position-tier median0.266-0.1070.26

Base rate — share of held-out pages truly in the bottom quartile of CTR: 0.26.

Read honestly: the model's average error was worse than the baseline's, and both have negative R² — neither beats simply predicting the mean CTR for every page. That is a real finding about the difficulty of this problem at 15,000 rows and 21 training clients, not a result I'm reframing as a win. But the metric that matters for a ranked action queue is precision@K, not average error — a rule that ties almost every page to one of three numbers can't differentiate within a tier, and its top-50 lands right at the base rate (no better than random). The model's richer, per-page predictions differentiate enough to catch true bottom-quartile pages 40% of the time in its top 50 — a real, if modest, edge for the one job this queue actually needs to do.

§6 · limitations

Limitations & honest framing

  • Scale. This runs on the 30,000-row starter release, not the ~79-million-row warehouse. The method is designed to port directly — same feature names confirmed present in the warehouse schema — but these numbers should be read as directional, not final, until re-run at full scale.
  • No causal claim. A model that predicts CTR association is not a claim that rewriting a listing will change it. Nothing here is a before/after experiment; recommendations below are decision-support, not guarantees.
  • Single-snapshot validation. The starter release is one 90-day snapshot, not a multi-month panel, so this is a client-holdout, not a genuine past-predicts-future temporal test. The full warehouse's monthly partitions would support a stronger design: train on early months, evaluate against a truly later month.
§7 · recommendations

Ranked recommendations — the action playbook

2,041 held-out-client pages — ones the model never trained on — were flagged where predicted CTR exceeds actual CTR, ranked by the size of that gap. Every flagged page carries the same reason code and action, by design: a single, readable rule a non-engineer can audit.

position_ok_ctr_below_tier_peers review_listing_ctr — rewrite title/meta for the highest-gap pages first; verify any exact-zero-CTR page actually resolves before assuming it's a listing problem, not a tracking one.
